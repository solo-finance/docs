The SOLO Network API uses standard HTTP status codes and returns JSON error
bodies. This page documents the response shapes, the error codes, and what
your integration should do with each.

## Error shapes

Errors raised by the API's domain logic return a consistent envelope. For
example, a `404`:

```json
{
  "detail": "Consent record not found",
  "error_code": "RESOURCE_NOT_FOUND",
  "request_id": "a1b2c3d4e5f60718293a4b5c6d7e8f90"
}
```

| Field | Type | Presence | Meaning |
| --- | --- | --- | --- |
| `detail` | string | always | Human-readable description. Safe to log; not guaranteed stable, so don't branch on its text. |
| `error_code` | string | always | Machine-readable category (see below). Branch on this. |
| `request_id` | string | when available | The request's ID. Quote it to SOLO. |
| `errors` | array | occasionally | Itemized sub-errors for operations that validate many things at once. |

Some responses use a **short shape** — just `{"detail": "..."}` with no
`error_code`:

- **`401` authentication failures**, raised while checking the bearer
  credential (see [Authentication](/home/authentication#401-vs-403)).
- **`422` request validation**, where the request is rejected before it reaches
  domain logic.
- A few endpoint-specific errors, such as the `400`, `502`, and `503` responses
  from the furnishing mapping dry-run endpoints.

```json
{ "detail": "body -> network_ids: Field required" }
```

### Error codes

| `error_code` | Status | Raised when |
| --- | --- | --- |
| `VALIDATION_ERROR` | `400` | The request was well-formed but the operation isn't valid (for example, consent not gathered) |
| `AUTHENTICATION_REQUIRED` | `401` | Domain logic could not establish who you are |
| `PERMISSION_DENIED` | `403` | You're authenticated but not allowed to do this (for example, your organization isn't a member of the network, lacks the furnisher role, or the consent has expired) |
| `RESOURCE_NOT_FOUND` | `404` | The referenced resource doesn't exist or isn't visible to you |
| `RESOURCE_CONFLICT` | `409` | The operation conflicts with existing state |
| `OPERATION_FAILED` | `500` | A known internal operation failed |
| `UNKNOWN_ERROR` | `500` | An application error without a more specific category |
| `INTERNAL_ERROR` | `500` | An unexpected error |

## HTTP status codes

| Code | Meaning on this API |
| --- | --- |
| `200 OK` | Success. The body contains the requested data. |
| `204 No Content` | A product query ran but produced **no result**: the available data did not satisfy the querying policy. The body is empty; the `X-Ref-Id` header identifies the query. |
| `400 Bad Request` | The request was structurally valid but the operation isn't (for example, a query that sends both `consent_id` and `consumer_identity_id`). |
| `401 Unauthorized` | Missing, invalid, or revoked credential, or one that doesn't resolve to an account. |
| `403 Forbidden` | Valid credential, but the operation isn't permitted. |
| `404 Not Found` | The resource doesn't exist, or isn't visible within the networks you named. |
| `409 Conflict` | The operation conflicts with current state. |
| `422 Unprocessable Entity` | A missing, mistyped, or malformed field. The `detail` string names the field path. |
| `500 Internal Server Error` | Something went wrong on SOLO's side. |
| `502` / `503` | Returned only by the AI-assisted mapping endpoints (`/v1/furnishing/mapping/suggest` and `/v1/furnishing/mapping/propose`) when the suggestion service is unavailable or busy. Retry shortly. |

<Note>
  A `204` is not an error. It means the query ran but the network could not
  assemble a result that meets the querying policy for this subject. Log the
  `X-Ref-Id` header before treating the response as "no data". To find out
  what was missing without running another billable query, use the soft check
  (`POST /v1/products/kyc_certificate_snapshot/query/soft`) and read its
  `missing_data_paths`.
</Note>

## Examples by status

    Creating a consumer consent without affirming consent was gathered:

    ```json
    {
      "detail": "Consent cannot be created without prior consumer consent gathering",
      "error_code": "VALIDATION_ERROR",
      "request_id": "a1b2c3d4e5f60718293a4b5c6d7e8f90"
    }
    ```

    Updating a consent with nothing to change:

    ```json
    {
      "detail": "At least one of scope, expires_at, or consented_fields must be provided",
      "error_code": "VALIDATION_ERROR",
      "request_id": "a1b2c3d4e5f60718293a4b5c6d7e8f90"
    }
    ```

    Querying a product with both a consent and a profile ID:

    ```json
    {
      "detail": "Provide either consent_id or consumer_identity_id, not both",
      "error_code": "VALIDATION_ERROR",
      "request_id": "a1b2c3d4e5f60718293a4b5c6d7e8f90"
    }
    ```

    Sending neither returns
    `"Either consent_id or consumer_identity_id must be provided"`.
  </Accordion>


    ```json
    { "detail": "Invalid or expired token" }
    ```

    ```json
    { "detail": "Could not validate API key" }
    ```

    ```json
    { "detail": "Could not validate credentials or find account" }
    ```
  </Accordion>

  <Accordion title="403 — permission denied">
    Furnishing into a network where your organization doesn't hold the
    furnisher or governor role:

    ```json
    {
      "detail": "Permission denied: cannot furnish network 9f1c0c2e-3d5b-4a89-b1e2-7f6a8c0d4e21",
      "error_code": "PERMISSION_DENIED",
      "request_id": "a1b2c3d4e5f60718293a4b5c6d7e8f90"
    }
    ```

    Querying with an expired consent:

    ```json
    {
      "detail": "Consent has expired",
      "error_code": "PERMISSION_DENIED",
      "request_id": "a1b2c3d4e5f60718293a4b5c6d7e8f90"
    }
    ```

    Consent, entity search, and furnish calls also return `403` when your
    organization isn't a member of the `network_id` you sent.
  </Accordion>

  <Accordion title="404 — resource not found">
    Reading or updating a consent with a `network_id` other than the one it was
    created in:

    ```json
    {
      "detail": "Consent record not found",
      "error_code": "RESOURCE_NOT_FOUND",
      "request_id": "a1b2c3d4e5f60718293a4b5c6d7e8f90"
    }
    ```

    A product query returns `404` when its consent belongs to a network that
    isn't in `network_ids`, when a `consumer_identity_id` isn't visible to you
    in those networks, or when an explicit `policy_id` doesn't exist or isn't
    available to you.

    <Note>
      `404` also covers resources that exist but are outside the networks you
      named — the API does not distinguish "doesn't exist" from "not visible to
      you".
    </Note>
  </Accordion>

  <Accordion title="422 — request validation">
    The `detail` is a single string in the form `<field path>: <message>`,
    where the path walks from the request part (`body`, `query`, `path`) down
    to the offending field. Only the **first** validation error is reported.

    ```json
    { "detail": "body -> consumer_consent_event_identity -> phone_number: Field required" }
    ```

    ```json
    { "detail": "query -> network_id: Field required" }
    ```

    Fix the named field and resend. The
    [API Reference](/api-reference/introduction) documents the type and format
    of every field.
  </Accordion>

  <Accordion title="500 — server error">
    Unexpected failures never include internal details:

    ```json
    {
      "detail": "An unexpected error occurred",
      "error_code": "INTERNAL_ERROR",
      "request_id": "a1b2c3d4e5f60718293a4b5c6d7e8f90"
    }
    ```

    Known internal failures return `OPERATION_FAILED` or `UNKNOWN_ERROR`
    instead. Include the request ID when reporting one.
  </Accordion>
</AccordionGroup>

## Validation errors vs domain errors

The status code tells you which kind of "bad request" you have:

- **`422` — the request itself is malformed.** A required field is missing, a
  date doesn't parse, a UUID is garbled. The request never reached business
  logic. Fix the payload; the body is the short shape with a
  `field path: message` detail.
- **`400` — the request is well-formed but the operation is invalid.** Every
  field parsed, but a business rule said no: consent wasn't gathered, an update
  contained nothing to change, or the combination of inputs isn't allowed. The
  body is the full envelope with `"error_code": "VALIDATION_ERROR"`.

Treat `422` as a bug in how your integration builds requests, and `400` as a
signal that this particular operation needs different inputs.

## Request IDs

Every request is assigned an ID when it enters the API. Responses carry it in
the `X-Request-ID` header, and error envelopes repeat it in the body as
`request_id`. Some error responses carry only one of the two, so read the body
field first and fall back to the header. Treat the value as an opaque string.

Product queries also return an `X-Ref-Id` header: the ID of the recorded query
event. On a `200` it matches the body's `provenance_event_id`; on a `204` it's
the only identifier you get.

When contacting SOLO about a failed call, include:

1. The request ID (and the `X-Ref-Id` for product queries).
2. The status code and full response body.
3. The endpoint, method, and approximate timestamp with timezone.

## Retries and idempotency

The API has no idempotency keys, and writes are not idempotent:

- **Retrying a product query** (`POST /v1/products/kyc_certificate_snapshot/query`
  and the other `query` endpoints) runs a new query. Queries are billable, so
  a retried query may be billed again.
- **Retrying a furnish** (`POST /v1/products/kyc_certificate_snapshot/furnish`
  or `POST /v1/products/kyb_certificate_snapshot/furnish`) matches the same
  subject again, but creates the verification events in the request again,
  which can leave duplicate event rows.
- **Retrying a consent create** creates another consent record.

If a write times out or fails with a `500` and you can't tell whether it took
effect, check before resending. For a furnish, a non-billable soft check
(`POST /v1/products/kyc_certificate_snapshot/query/soft`) lists the certificate
models that now have data (`matched_models`); entity search confirms the
subject exists. Searches, consent reads, and the non-billable checks are safe
to retry.

| Status | Retry? | How |
| --- | --- | --- |
| `500` | Reads: yes. Writes: check first | Retry reads with exponential backoff and jitter. For queries, furnishes, and consent creates, confirm the first attempt didn't take effect before resending. If it persists, stop and report the request ID. |
| `502`, `503` (mapping suggest and propose) | Yes | Retry after a short delay. |
| `401` | After fixing the credential | Retrying with the same credential fails the same way. |
| `409` | Maybe | Re-read current state first; retry only if the conflict is resolved. |
| `400`, `403`, `404`, `422` | No | The same request fails the same way. Fix the request, your roles, or the referenced resource. |
| `204` | No | Not an error. Re-query only when you expect the underlying data to have changed. |

There are no published rate limits. Cap retry attempts anyway, so a transient
failure doesn't turn into a loop of billable queries.
