Every public endpoint under `/v1` requires a bearer credential in the
`Authorization` header:

```bash
Authorization: Bearer <credential>
```

Only `GET /health` and `GET /version` are exempt; everything else returns
`401 Unauthorized` without a valid credential.

The API accepts two kinds of credential, both issued through **WorkOS**, SOLO's
identity provider:

| Credential | Use it for | Where it comes from |
| --- | --- | --- |
| **Organization API key** | Server-to-server integrations. This is the credential to build against. | Created in the SOLO dashboard under **Settings → API keys** |
| **Dashboard session token** | Requests made by the SOLO dashboard on behalf of a signed-in user | Issued when a user signs in to the dashboard |

## Create an API key

<Steps>
  <Step title="Get a dashboard account">
    SOLO sets up your organization's dashboard account and adds it to one or
    more networks. Start in sandbox: sign in at
    [app.sandbox.solo.one](https://app.sandbox.solo.one). See
    [Getting access](/home/quickstart#getting-access).
  </Step>
  <Step title="Create the key">
    In the dashboard, open **Settings → API keys** and create a key. Give it a
    name that identifies the integration using it. The same page lists your
    organization's keys and lets you revoke them.
  </Step>
  <Step title="Store it and send it">
    Keep the key in a secrets manager or an environment variable, and send it
    as a `Bearer` credential on every request. The examples on this site read
    it from `$SOLO_TOKEN`:

    ```bash
    export SOLO_TOKEN="<your API key>"
    ```
  </Step>
</Steps>

API keys belong to your **organization**, not to a user. A request made with a
key acts as your organization's account on the network, with all of the
organization's network memberships and roles — keys have no narrower scopes of
their own. The same key is also what authenticates
[SFTP uploads](/api-overview/sftp/getting-started).

<Warning>
  Treat API keys as secrets. Never commit them to source control, embed them in
  client-side code, or log them. Anyone holding a key can act as your
  organization until the key is revoked.
</Warning>

## What the server verifies

The API checks the credential before any handler runs:

1. **Credential type.** A value shaped like a JWT (three dot-separated
   segments) is treated as a dashboard session token. Anything else is treated
   as an organization API key.
2. **Session tokens** are verified locally: the signature is checked against
   WorkOS's published signing keys
   (`https://api.workos.com/sso/jwks/<client_id>`) and the expiry is enforced.
3. **API keys** are validated with WorkOS. Only keys owned by an organization
   are accepted. A successful validation is cached briefly (by default for up
   to 60 seconds), so a key you revoke can keep working for that long.
4. **Account resolution.** The verified identity is mapped to an account on
   the network:
   - An API key resolves to the account of the organization that owns it. SOLO
     links your organization to its network account during onboarding; a valid
     key from an organization that isn't linked yet gets
     `401 Could not validate API key`.
   - A session token resolves to the signed-in user's account. A user's first
     authenticated request provisions their account, attached to their
     organization by email domain.

Authenticating doesn't by itself give access to any data. Reading and writing
data in a network still requires your organization to be a member of it, with
the right role.

## Environments

Sandbox and production are separate deployments with separate data. Create
sandbox keys in the sandbox dashboard and use them against the sandbox API; do
the same for production.

| Environment | API base URL                   | Dashboard (create keys here)   |
| ----------- | ------------------------------ | ------------------------------ |
| Sandbox     | `https://api.sandbox.solo.one` | `https://app.sandbox.solo.one` |
| Production  | `https://api.solo.one`         | `https://app.solo.one`         |

## Example request

Search for a consumer by name within a network with
`GET /v1/entities/consumer_identity/search`:

```bash
curl -G "https://api.sandbox.solo.one/v1/entities/consumer_identity/search" \
  -H "Authorization: Bearer $SOLO_TOKEN" \
  --data-urlencode "network_id=9f1c0c2e-3d5b-4a89-b1e2-7f6a8c0d4e21" \
  --data-urlencode "first_name=Jane" \
  --data-urlencode "last_name=Doe" \
  --data-urlencode "limit=10"
```

A successful response returns the matching consumers visible to you in that
network:

```json
[
  {
    "id": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
    "identifier": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
    "created_at": "2026-05-12T18:21:43+00:00",
    "updated_at": "2026-05-12T18:21:43+00:00",
    "first_name": "Jane",
    "last_name": "Doe",
    "personal_email": "jane.doe@example.com",
    "date_of_birth": "1990-01-15",
    "social_security_number": "123-45-6789"
  }
]
```

The same header works on every endpoint.

## 401 vs 403

The two failure modes mean different things, and you should handle them
differently.

**`401 Unauthorized` — the API couldn't establish who you are.** The
credential is missing, malformed, invalid, revoked, or doesn't resolve to an
account. These responses use a short body with only a `detail` field:

```json
{ "detail": "Requires authentication" }
```

```json
{ "detail": "Invalid or expired token" }
```

```json
{ "detail": "Could not validate API key" }
```

```json
{ "detail": "Could not validate credentials or find account" }
```

**`403 Forbidden` — the API knows who you are, and the answer is no.** The
credential is valid, but the operation isn't allowed — for example, calling a
network your organization isn't a member of, furnishing into a network where it
doesn't hold the furnisher role, or querying with an expired consent. These use the full error envelope with
`"error_code": "PERMISSION_DENIED"`; see [Errors](/home/errors). Retrying with
the same credential fails the same way.

<Tip>
  Rule of thumb: on `401`, check the credential — a revoked key or a typo in
  the header. On `403`, check your organization's roles and network membership
  or the consent you used — retrying won't help.
</Tip>

## Troubleshooting

| Symptom | Status and `detail` | Cause | Fix |
| --- | --- | --- | --- |
| No `Authorization` header | `401` — `Requires authentication` | Header missing | Add `Authorization: Bearer $SOLO_TOKEN` |
| Wrong scheme (e.g. `Authorization: Token …` or a bare key) | `401` — `Requires authentication` | Only the `Bearer` scheme is read, so the header is treated as absent | Use exactly `Bearer <credential>` |
| Revoked, mistyped, or unknown API key | `401` — `Invalid or expired token` | WorkOS didn't validate the key | Re-copy the key, or create a new one in **Settings → API keys** |
| Key from the other environment | `401` — `Invalid or expired token` or `Could not validate API key` | The key wasn't created for this environment | Use a key created in this environment's dashboard |
| Valid key, organization not yet linked | `401` — `Could not validate API key` | Your organization isn't linked to a network account in this environment | Contact your SOLO contact to finish onboarding |
| Expired or malformed session token | `401` — `Invalid or expired token` | The token's signature or expiry check failed | Sign in again; use an API key for server-to-server calls |
| Session token whose user can't be mapped to an account | `401` — `Could not validate credentials or find account` | No account could be resolved or provisioned for the user | Contact your SOLO contact |
| Persistent `500` — `Authentication service is unavailable` | `500` | A server-side identity configuration problem, not your credential | Report it to SOLO with the `X-Request-ID` response header |

If you're stuck, capture the full response — including the `X-Request-ID`
header — and quote it to SOLO. See [Errors](/home/errors#request-ids).

## Best practices

<AccordionGroup>
  <Accordion title="Keep keys server-side">
    Make API calls from your backend. An API key carries your organization's
    full standing on the network until it is revoked.
  </Accordion>
  <Accordion title="One key per integration">
    Create a separate, clearly named key for each system that calls the API. If
    one system is compromised or retired, you can revoke its key without
    disturbing the others.
  </Accordion>
  <Accordion title="Rotate without downtime">
    To rotate, create a new key, deploy it, confirm traffic is using it, then
    revoke the old key. Allow for the short validation cache: a revoked key can
    keep working for up to a minute by default.
  </Accordion>
  <Accordion title="Store the key in an environment variable or secrets manager">
    Keeping the key out of code keeps it out of shell history, scripts, and
    version control.
  </Accordion>
</AccordionGroup>
