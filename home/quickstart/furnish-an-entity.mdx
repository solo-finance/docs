Furnishing contributes data about a
[consumer or business](/concepts/identity/entities) into a
[network](/concepts/governance/networks). In this guide you'll record a
consumer's [consent](/concepts/identity/consent), then furnish the verification
events behind a KYC certificate for them. Furnishing is also how you earn
[entitlement](/concepts/governance/entitlement) — once you've contributed data
about a consumer, you can read that consumer's data back on future queries.

## Prerequisites

<Note>
  Before you start, you need:

  - **The furnisher (or governor) role in a network** — see
    [Getting access](/home/quickstart#getting-access).
  - **A sandbox API key** exported as `SOLO_TOKEN`. See
    [Authentication](/home/authentication).
  - **Your `network_id`** — the network you furnish into.
</Note>

## Record consent and furnish

<Steps>
  <Step title="Record the consumer's consent">
    Create a consent record with the consumer's identity, attesting that you
    gathered their permission:

    ```bash
    curl -X POST https://api.sandbox.solo.one/v1/consent/consumer_identity \
      -H "Authorization: Bearer $SOLO_TOKEN" \
      -H "Content-Type: application/json" \
      -d '{
        "network_id": "9f1c0c2e-3d5b-4a89-b1e2-7f6a8c0d4e21",
        "did_gather_consent_from_consumer_prior": true,
        "consumer_consent_event_identity": {
          "first_name": "Jane",
          "last_name": "Doe",
          "date_of_birth": "1990-01-15T00:00:00",
          "personal_email": "jane.doe@example.com",
          "phone_number": "5551234567",
          "social_security_number": "123-45-6789"
        }
      }'
    ```

    ```json Response
    {
      "consent_id": "5f3a8c21-09d4-4b7a-9d52-6e8b1f4c2a30",
      "model_access_grants": [
        {
          "furnishing_entity_id": null,
          "models": ["fraud_verification_event"],
          "effective_from": "2026-06-09",
          "effective_to": null
        }
      ],
      "created_at": "2026-06-09T22:04:11+00:00",
      "events": "",
      "scope": "",
      "expires_at": null,
      "consented_fields": null
    }
    ```

    All six identity fields are required. If you already know the consumer's
    profile ID (for example from an
    [entity search](/home/quickstart/join-a-network)), pass it as the optional
    `consumer_identity_id` to link the consent to that profile.

    The consent is bound to the network you created it in. Look it up — and
    query with it — using that same network. Your organization must be a
    member of `network_id`, or the request returns `403`.

    <Warning>
      `did_gather_consent_from_consumer_prior` is an attestation, not a flag.
      Only set it to `true` if you have actually obtained the consumer's
      permission — the API rejects the request with a `400` otherwise.
    </Warning>

    You can re-fetch the consent at any time; the response has the same shape
    as the create response:

    ```bash
    curl -G https://api.sandbox.solo.one/v1/consent/consumer_identity/5f3a8c21-09d4-4b7a-9d52-6e8b1f4c2a30 \
      -H "Authorization: Bearer $SOLO_TOKEN" \
      --data-urlencode "network_id=9f1c0c2e-3d5b-4a89-b1e2-7f6a8c0d4e21"
    ```
  </Step>

  <Step title="Build the record">
    Each furnish record identifies one consumer and carries the verification
    events you performed for them. Four identity fields are required:
    `first_name`, `last_name`, `date_of_birth`, and `social_security_number`.
    The network matches the record to an existing consumer on **SSN and date
    of birth**, or creates the consumer if there is no match, and stores the
    events attributed to your organization.

    A KYC certificate is assembled from five kinds of verification evidence:
    document, biometric, liveness, address, and identity corroboration. This
    record furnishes one event of each:

    ```json
    {
      "first_name": "Jane",
      "last_name": "Doe",
      "date_of_birth": "1990-01-15",
      "social_security_number": "123-45-6789",
      "document_capture_events": [
        {
          "is_document_captured": true,
          "document_capture_timestamp": "2026-06-08",
          "document_capture_method": "mobile_live_capture",
          "is_document_attribute_reviewed": true,
          "document_attribute_review_timestamp": "2026-06-08",
          "document_review_method": "automated_and_manual",
          "document_review_evidence_source": "commercial_verification_provider"
        }
      ],
      "biometric_capture_events": [
        {
          "is_biometric_captured": true,
          "biometric_capture_timestamp": "2026-06-08",
          "biometric_capture_method": "live_selfie_video",
          "is_biometric_attribute_reviewed": true,
          "biometric_attribute_review_timestamp": "2026-06-08",
          "is_biometric_comparison_performed": true,
          "biometric_comparison_reference": "document_photo_same_session",
          "biometric_comparison_outcome": "full_match"
        }
      ],
      "liveness_check_events": [
        {
          "is_liveness_captured": true,
          "capture_timestamp": "2026-06-08",
          "capture_method_type": "passive_liveness",
          "check_result": "live_person_confirmed",
          "is_liveness_evidence_reviewed": true,
          "evidence_review_timestamp": "2026-06-08"
        }
      ],
      "identity_corroboration_events": [
        {
          "identity_corroboration_timestamp": "2026-06-08",
          "identity_corroboration_methods": ["credit_bureau_match"],
          "identity_corroboration_outcome": "full_match",
          "is_kyc_cip": true,
          "total_identity_corroboration_sources_consulted": 2,
          "is_ssn_match": true,
          "is_dob_match": true,
          "is_name_match": true
        }
      ],
      "address_identities": [
        {
          "line_1": "123 Main St",
          "city": "Springfield",
          "state": "IL",
          "zip": "62701",
          "country": "US",
          "address_capture_events": [
            {
              "is_address_captured": true,
              "address_capture_timestamp": "2026-06-08",
              "is_address_verified": true,
              "address_verification_timestamp": "2026-06-08",
              "address_verification_method_type": "credit_bureau_match",
              "address_verification_outcome": "full_match",
              "deliverable": true
            }
          ]
        }
      ]
    }
    ```

    Every event list is optional — furnish whatever evidence you actually hold.
    `records` is a list, so you can batch many consumers into one call.
  </Step>

  <Step title="Confirm the consumer is visible">
    The furnished consumer now appears in entity search for the network:

    ```bash
    curl -G https://api.sandbox.solo.one/v1/entities/consumer_identity/search \
      -H "Authorization: Bearer $SOLO_TOKEN" \
      --data-urlencode "network_id=9f1c0c2e-3d5b-4a89-b1e2-7f6a8c0d4e21" \
      --data-urlencode "social_security_number=123-45-6789"
    ```

    A `200` with a matching record confirms the furnish landed. To see whether
    the evidence you furnished is enough for a certificate, run the
    non-billable soft check described in
    [Query a product](/home/quickstart/query-a-product).
  </Step>
</Steps>

## Inspect the result

**Consent response** (step 1):

| Field | Meaning |
|---|---|
| `consent_id` | The ID you pass on later queries of this consumer. Store it. |
| `model_access_grants` | The access grants attached to the consent. Each lists the data `models` it covers, the `furnishing_entity_id` it's limited to (`null` = any furnisher), and its `effective_from` / `effective_to` window. |
| `created_at` | When the consent record was created. |
| `events` | The consent's event log reference (empty for a new consent). |
| `scope` | The consent's scope label. Starts empty; updatable later. |
| `expires_at` | When the consent lapses. `null` means no expiry has been set. |
| `consented_fields` | An optional restriction of consented fields. `null` means none. |

**Furnish response** (step 3):

| Field | Meaning |
|---|---|
| `success` | `true` — the records were accepted. |
| `profile_ids` | The consumer profile ID each record matched or created, in request order. Use it as `consumer_identity_id` elsewhere in the API. |
| `counts` | How many rows were submitted per kind of event or nested record, across all records. |

<Tip>
  Identity fields on a consent are immutable — a consent record is an audit
  artifact of who consented and when. To consent with different identity data,
  create a new consent record. `scope`, `expires_at`, and `consented_fields`
  can be changed with `PUT /v1/consent/consumer_identity/{consent_id}`.
</Tip>

<Warning>
  Furnish calls are not idempotent. Resending the same request matches the same
  consumer but records the events again. If a furnish times out, check before
  retrying — see [Retries and idempotency](/home/errors#retries-and-idempotency).
</Warning>

## Why consent comes first

Furnishing contributes data *about* a person, and the consent record is the
audit artifact showing they agreed: who consented, when, and through which
identity. The same `consent_id` is what you pass when you later
[query this consumer back](/home/quickstart/query-a-product) in the same
network. The full model is covered in [Consent](/concepts/identity/consent).

## Furnishing at scale

A JSON furnish accepts many `records` per call, which covers most integration
patterns. For recurring volume:

- **SFTP ingestion** — deliver JSONL files on a schedule and let the platform
  ingest them automatically. Start with
  [SFTP getting started](/api-overview/sftp/getting-started).
- **File uploads** — the JSONL format, record types, and per-record results are
  covered in [JSONL files](/api-overview/furnishing/file-upload).

## Troubleshooting

<AccordionGroup>
  <Accordion title="401 — credential not accepted">
    ```json
    { "detail": "Invalid or expired token" }
    ```

    The API key is missing, mistyped, or revoked. Check `SOLO_TOKEN`, or create
    a new key in the dashboard under **Settings → API keys**. See
    [Authentication](/home/authentication#troubleshooting).
  </Accordion>
  <Accordion title="400 — consent not gathered">
    ```json
    {
      "detail": "Consent cannot be created without prior consumer consent gathering",
      "error_code": "VALIDATION_ERROR"
    }
    ```

    You sent `did_gather_consent_from_consumer_prior: false`. Gather consent,
    then retry with `true`.
  </Accordion>
  <Accordion title="404 — consent not found in this network">
    ```json
    {
      "detail": "Consent record not found",
      "error_code": "RESOURCE_NOT_FOUND"
    }
    ```

    Returned by `GET /v1/consent/consumer_identity/{consent_id}` when the
    `network_id` doesn't match the network the consent was created in. Use the
    same `network_id` you created it under.
  </Accordion>
  <Accordion title="403 — missing the furnisher role">
    ```json
    {
      "detail": "Permission denied: cannot furnish network 9f1c0c2e-3d5b-4a89-b1e2-7f6a8c0d4e21",
      "error_code": "PERMISSION_DENIED"
    }
    ```

    Your key is valid, but your organization doesn't hold the furnisher or
    governor role in that network. Check the network's **Members** tab in the
    dashboard, and see [Network roles](/concepts/governance/network-roles).
  </Accordion>
  <Accordion title="422 — missing or malformed field">
    ```json
    { "detail": "body -> network_id: Field required" }
    ```

    A required field is missing or has the wrong type. The `detail` string names
    the first failing field — common culprits are omitting `network_id`,
    or leaving an identity field out of `consumer_consent_event_identity`.
  </Accordion>
</AccordionGroup>
