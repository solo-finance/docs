Querying reads a consolidated result about a subject from one or more
[networks](/concepts/governance/networks). In this guide you'll use a
[consent](/concepts/identity/consent) record to check, without being billed,
whether a KYC certificate can be issued for a consumer — and then query it.

## Prerequisites

<Note>
  Before you start, you need:

  - **Membership in the network you query** — see
    [Getting access](/home/quickstart#getting-access).
  - **A sandbox API key** exported as `SOLO_TOKEN`. See
    [Authentication](/home/authentication).
  - **Your `network_id`**. Optionally, the `policy_id` of a
    [querying policy](/concepts/governance/querying-policies) — if you omit
    it, the policy assigned to the first network you query applies.
</Note>

## Consent, check, query

<Steps>
  <Step title="Create or reuse a consent record">
    If you already hold a valid `consent_id` for this consumer — for example
    from [Furnishing your first entity](/home/quickstart/furnish-an-entity) —
    reuse it. Otherwise, create one:

    ```bash
    curl -X POST https://api.sandbox.solo.one/v1/consent/consumer_identity \
      -H "Authorization: Bearer $SOLO_TOKEN" \
      -H "Content-Type: application/json" \
      -d '{
        "network_id": "9f1c0c2e-3d5b-4a89-b1e2-7f6a8c0d4e21",
        "did_gather_consent_from_consumer_prior": true,
        "consumer_consent_event_identity": {
          "first_name": "Jane",
          "last_name": "Doe",
          "date_of_birth": "1990-01-15T00:00:00",
          "personal_email": "jane.doe@example.com",
          "phone_number": "5551234567",
          "social_security_number": "123-45-6789"
        }
      }'
    ```

    Keep the `consent_id` from the response. The consent is bound to the
    network it was created in, so every query that uses it must include that
    network in `network_ids`.

    <Warning>
      `did_gather_consent_from_consumer_prior` is an attestation. Only send
      `true` if you have actually obtained the consumer's permission; the API
      rejects `false` with a `400`.
    </Warning>
  </Step>

  <Step title="Soft check: would the query produce a certificate?">
    A query is billable. The soft check takes the exact same request body,
    runs the same resolution, and tells you whether a certificate would be
    issued — without billing you, issuing a certificate, or returning any data
    values:

    ```bash
    curl -X POST https://api.sandbox.solo.one/v1/products/kyc_certificate_snapshot/query/soft \
      -H "Authorization: Bearer $SOLO_TOKEN" \
      -H "Content-Type: application/json" \
      -d '{
        "consent_id": "5f3a8c21-09d4-4b7a-9d52-6e8b1f4c2a30",
        "network_ids": ["9f1c0c2e-3d5b-4a89-b1e2-7f6a8c0d4e21"]
      }'
    ```

    ```json Response
    {
      "issuable": true,
      "missing_data_paths": [],
      "matched_models": [
        "AddressCaptureEvent",
        "BiometricCaptureEvent",
        "DocumentCaptureEvent",
        "IdentityCorroborationEvent",
        "LivenessCheckEvent"
      ]
    }
    ```

    - `issuable` — whether the same query would return a certificate (`200`)
      rather than `204`.
    - `matched_models` — the kinds of verification evidence found for this
      consumer.
    - `missing_data_paths` — certificate fields the querying policy requires
      that are still empty. Empty when `issuable` is `true`.

    If `issuable` is `false`, the query would return `204`. Furnish the missing
    evidence (see
    [Furnishing your first entity](/home/quickstart/furnish-an-entity)) or
    query different networks, then check again. To see which furnishers hold
    data for the consumer, use the non-billable
    [coverage check](/api-overview/querying/coverage-check)
    (`POST /v1/products/check`).
  </Step>

  <Step title="Query the KYC certificate">
    Send the same body to the query endpoint. `network_ids` takes one or more
    networks; the optional `policy_id` is applied across all of them:

    ```bash
    curl -X POST https://api.sandbox.solo.one/v1/products/kyc_certificate_snapshot/query \
      -H "Authorization: Bearer $SOLO_TOKEN" \
      -H "Content-Type: application/json" \
      -d '{
        "consent_id": "5f3a8c21-09d4-4b7a-9d52-6e8b1f4c2a30",
        "network_ids": ["9f1c0c2e-3d5b-4a89-b1e2-7f6a8c0d4e21"]
      }'
    ```

    The response below is abridged to two of the nine sub-products:

    ```json Response
    {
      "certificate_id": "8a6f4c2e-1b9d-4730-a5e8-3c7f0d2b6491",
      "provenance_event_id": "c1e8f5a3-7d20-4b96-8c44-e6a9b3d1f728",
      "consumer_identity_id": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
      "result": {
        "meta": {
          "network_id": "9f1c0c2e-3d5b-4a89-b1e2-7f6a8c0d4e21",
          "policy_id": "5e7d2a14-8b3c-4f60-9e17-a2d4c6b8f015"
        },
        "document_capture": {
          "furnishing_entity_id": "3e2d1c0b-9a87-4654-b321-0f9e8d7c6b5a",
          "attestation_event_id": "f0a9b8c7-d6e5-4432-a1b0-c9d8e7f6a5b4",
          "assertions": {
            "document_capture_assertion": true,
            "document_capture_timestamp": "2026-06-08T00:00:00"
          },
          "data": {
            "document_artifact": null,
            "document_type": null,
            "document_issuing_state": null,
            "document_number": null,
            "document_issue_date": null,

            "document_capture_method": "mobile_live_capture"
          }
        },
        "document_review": {
          "furnishing_entity_id": "3e2d1c0b-9a87-4654-b321-0f9e8d7c6b5a",
          "attestation_event_id": "f0a9b8c7-d6e5-4432-a1b0-c9d8e7f6a5b4",
          "assertions": {
            "document_attribute_review_assertion": true,
            "document_attribute_review_timestamp": "2026-06-08T00:00:00"
          },
          "data": {
            "document_review_method": "automated_and_manual",
            "document_review_evidence_source": "commercial_verification_provider",
            "document_tamper_review_performed": null,

            "is_document_machine_readable_data_validation_performed": null,
    ```

    To restrict the query to specific furnishers, add the optional
    `furnishing_entity_ids` list; when omitted, data from all furnishers is
    considered.
  </Step>
</Steps>

## Request rules

- **`network_ids`** is required and needs at least one network. If you use a
  `consent_id`, the network the consent was created in must be in the list, or
  the query returns `404`.
- **Identify the subject one way.** Send either `consent_id` or
  `consumer_identity_id` (the consumer's profile ID), not both — sending both
  returns `400`, and sending neither returns `400`. A `consumer_identity_id`
  must be a consumer visible to you in the queried networks, or the query
  returns `404`.
- **Expired consent.** A query with a consent whose `expires_at` has passed
  returns `403`.
- **`policy_id`** is optional. If you send one that doesn't exist, the query
  returns `404`. If you omit it, the querying policy assigned to the first
  network in `network_ids` applies to every network in the query;
  `result.meta.policy_id` tells you which policy was used.

## 200 vs 204, and the X-Ref-Id header

A query has two healthy outcomes:

- **`200 OK`** — the available data satisfied the querying policy and a
  certificate was issued. The body is the consolidated result above.
- **`204 No Content`** — the query ran, but no certificate could be issued from
  the data available to you. The body is empty. The soft check in step 2
  predicts this.

Both outcomes carry an **`X-Ref-Id` response header** — the ID of the recorded
query event. On a `200` it equals the body's `provenance_event_id`; on a `204`
it's the only identifier you get, so log it.

## Inspect the result

| Field | Meaning |
|---|---|
| `certificate_id` | ID of the certificate issued by this query. |
| `provenance_event_id` | ID of the recorded query event; matches the `X-Ref-Id` header. |
| `consumer_identity_id` | The consumer the query resolved to. |
| `result.meta` | The `network_id` the result is attributed to (the first in `network_ids`) and the `policy_id` applied (`null` if no policy applied). |
| `result.document_capture` … `result.identity_corroboration` | The nine certificate sub-products: document capture and review, biometric capture and review, liveness capture and review, address capture and verification, and identity corroboration. Each populated sub-product carries the `furnishing_entity_id` and `attestation_event_id` of the furnished record it came from, an `assertions` block (what was asserted and when), and a `data` block with the detail fields. |

If a field you expected is `null`, it's usually because it wasn't furnished,
you haven't earned entitlement to it, or the querying policy doesn't expose it
in this network.

## Maintaining the consent

Reuse one `consent_id` for every query of the same consumer in the same network
while the consent is valid. Its identity fields are immutable, but you can
change `scope`, `expires_at`, and `consented_fields`:

```bash
curl -X PUT https://api.sandbox.solo.one/v1/consent/consumer_identity/5f3a8c21-09d4-4b7a-9d52-6e8b1f4c2a30 \
  -H "Authorization: Bearer $SOLO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "network_id": "9f1c0c2e-3d5b-4a89-b1e2-7f6a8c0d4e21",
    "expires_at": "2027-01-01T00:00:00+00:00"
  }'
```

The response is the updated consent in the same shape as the create response.
At least one updatable field must be present, and `network_id` must be the
network the consent was created in.

There is no endpoint to revoke a consent. To end one early — for example, when
the consumer withdraws permission — set its `expires_at` to the current time
with the same request. Queries that use it then return `403`.

## Troubleshooting

<AccordionGroup>
  <Accordion title="401 — credential not accepted">
    ```json
    { "detail": "Invalid or expired token" }
    ```

    The API key is missing, mistyped, or revoked. See
    [Authentication](/home/authentication#troubleshooting).
  </Accordion>
  <Accordion title="400 — subject not identified correctly">
    ```json
    {
      "detail": "Provide either consent_id or consumer_identity_id, not both",
      "error_code": "VALIDATION_ERROR"
    }
    ```

    Send exactly one of `consent_id` or `consumer_identity_id`. Sending neither
    returns `"Either consent_id or consumer_identity_id must be provided"`.
  </Accordion>
  <Accordion title="403 — consent expired">
    ```json
    {
      "detail": "Consent has expired",
      "error_code": "PERMISSION_DENIED"
    }
    ```

    The consent's `expires_at` has passed. Create a new consent, or extend this
    one with `PUT /v1/consent/consumer_identity/{consent_id}` if the consumer's
    permission still stands.
  </Accordion>
  <Accordion title="404 — consent, consumer, or policy not found">
    Common causes: the consent was created in a network that isn't in
    `network_ids`; the `consent_id` doesn't exist; the `consumer_identity_id`
    isn't visible to you in those networks; or the `policy_id` doesn't exist.
    Check the consent with `GET /v1/consent/consumer_identity/{consent_id}`
    using the network it was created in.
  </Accordion>
  <Accordion title="422 — missing required field">
    ```json
    { "detail": "body -> network_ids: Field required" }
    ```

    `network_ids` (with at least one entry) is required on every query. The
    `detail` names the first invalid input.
  </Accordion>
  <Accordion title="204 — query ran but no certificate">
    Empty body, status `204`, with an `X-Ref-Id` header. The data available to
    you didn't satisfy the querying policy. Run the soft check
    (`POST /v1/products/kyc_certificate_snapshot/query/soft`) and read
    `missing_data_paths` to see what's missing.
  </Accordion>
</AccordionGroup>
