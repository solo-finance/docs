Everything you do with data happens inside a
[network](/concepts/governance/networks) — a group of participants that defines
who can contribute data, who can read it, and under which policies. This guide
explains how your organization becomes a member, then confirms your access with
two read-only calls.

## Prerequisites

<Note>
  Before you start, you need:

  - **A sandbox dashboard account and API key** — see
    [Getting access](/home/quickstart#getting-access).
  - **Your API key** exported as `SOLO_TOKEN`. See
    [Authentication](/home/authentication).
  - **Your `network_id`** — shown in the page URL when you open the network in
    the dashboard.
</Note>

## Set up and verify

<Steps>
  <Step title="Get added to a network">
    There is no REST endpoint for joining a network. Membership is managed in
    the SOLO dashboard: SOLO or the network's governor adds your organization,
    or you ask to join a network listed in the dashboard and its governor
    approves the request. When your organization is a member, it holds one or
    more **roles** in that network:

    | Role | What it lets you do |
    |---|---|
    | **Furnisher** | Contribute data into the network. |
    | **Querier** | Run product queries against the network. |
    | **Governor** | Administer the network's policies and membership. Governors can also furnish. |

    Your organization's roles are listed on the network's **Members** tab in
    the dashboard. Roles grant *capabilities*, not *visibility*: joining a
    network — even governing one — does not let you read other members' data
    on its own. What you can read is bounded by the querying policy and your
    [entitlement](/concepts/governance/entitlement). Roles are covered in depth
    in [Network roles](/concepts/governance/network-roles).
  </Step>

  <Step title="Confirm the API is reachable">
    `GET /version` needs no credential and confirms you can reach the API. It
    returns the API versions the deployment serves (`["v1"]`) and the build's
    version and commit — include those when reporting unexpected behavior.

    ```bash
    curl https://api.sandbox.solo.one/version
    ```

    There's also `GET /health`, which returns `{"status": "healthy"}` when the
    service is up; point uptime monitoring at it.
  </Step>

  <Step title="Verify your network access">
    The quickest end-to-end check of your key, your organization's account, and
    your `network_id` is an entity search scoped to the network:

    ```bash
    curl -G https://api.sandbox.solo.one/v1/entities/consumer_identity/search \
      -H "Authorization: Bearer $SOLO_TOKEN" \
      --data-urlencode "network_id=9f1c0c2e-3d5b-4a89-b1e2-7f6a8c0d4e21" \
      --data-urlencode "last_name=Doe" \
      --data-urlencode "limit=10"
    ```

    ```json Response
    [
      {
        "id": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
        "identifier": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
        "created_at": "2026-05-12T18:21:43+00:00",
        "updated_at": "2026-05-12T18:21:43+00:00",
        "first_name": "Jane",
        "last_name": "Doe",
        "personal_email": "jane.doe@example.com",
        "date_of_birth": "1990-01-15",
        "social_security_number": "123-45-6789"
      }
    ]
    ```

    A `200 OK` — even with an empty `[]` body — proves your key is accepted
    and the network is reachable. `network_id` is the only required
    parameter; the rest narrow the search:

    - `first_name`, `last_name`, `personal_email` — case-insensitive
      **partial** matches.
    - `social_security_number`, `date_of_birth` — **exact** matches
      (`YYYY-MM-DD` for date of birth).
    - `limit` — maximum results, 1–100, default 20. There is no offset or
      paging, so narrow your filters if you need to find a specific person.
  </Step>
</Steps>

## Inspect the result

Search returns only consumers visible to you in the network you named:

| Field | Meaning |
|---|---|
| `id` | The consumer's profile ID. Use it as `consumer_identity_id` when linking a consent or querying by profile. |
| `identifier` | The same ID, as a string. |
| `created_at` / `updated_at` | When the consumer record was created and last modified. |
| `first_name`, `last_name`, `personal_email`, `date_of_birth`, `social_security_number` | The consumer's core identity fields. Any of these may be `null` if not on file. |

An empty array is a healthy response — no consumer visible to you in this
network matches your filters yet. After you complete
[Furnishing your first entity](/home/quickstart/furnish-an-entity), the consumer
you furnish will appear here.

Search does *not* return certificates, events, or any product data. Reading
verification data about a consumer always goes through a product query.

The business equivalent is `GET /v1/entities/business_identity/search`, which
filters on `business_legal_name`, `business_dba_name`, `business_email`, and
`federal_ein`, with the same `network_id` and `limit` rules.

## Troubleshooting

<AccordionGroup>
  <Accordion title="401 — credential not accepted">
    ```json
    { "detail": "Invalid or expired token" }
    ```

    The key is missing, mistyped, or revoked. Confirm the header reads exactly
    `Authorization: Bearer $SOLO_TOKEN`, and that the key was created in the
    sandbox dashboard. A `Could not validate API key` detail means your
    organization isn't fully set up in this environment yet — contact your SOLO
    contact. See [Authentication](/home/authentication#troubleshooting).
  </Accordion>
  <Accordion title="422 — missing required parameter">
    ```json
    { "detail": "query -> network_id: Field required" }
    ```

    `network_id` is required on every search. A `422` carries a single
    `detail` string naming the first invalid input.
  </Accordion>
  <Accordion title="403 — role doesn't permit the operation">
    ```json
    {
      "detail": "Permission denied: cannot furnish network 9f1c0c2e-3d5b-4a89-b1e2-7f6a8c0d4e21",
      "error_code": "PERMISSION_DENIED"
    }
    ```

    Your key is valid but your organization's role in this network doesn't
    allow the call — here, furnishing without the furnisher role. Check the
    network's **Members** tab, and see
    [Network roles](/concepts/governance/network-roles).
  </Accordion>
  <Accordion title="200 with an empty array">
    Not an error. Your key and membership are fine; no consumer visible to you
    matches your filters. Partial-match fields (`first_name`, `last_name`,
    `personal_email`) are the most forgiving way to probe for data.
  </Accordion>
</AccordionGroup>
