The SOLO Network API reference is generated from the API's OpenAPI
specification. Each endpoint includes request and response schemas, parameter
details, and example payloads.

New to the platform? Read [High-level concepts](/home/overview) first — the
reference assumes familiarity with networks, entities, consent, products,
policies, and entitlement.

This reference covers the REST API. To read the data graph directly or furnish
nested records in one call, see the [GraphQL API](/api-overview/graphql/overview).

## Base URLs

| Environment | Base URL                       |
| ----------- | ------------------------------ |
| Sandbox     | `https://api.sandbox.solo.one` |
| Production  | `https://api.solo.one`         |

## Authentication

Every `/v1` endpoint requires a bearer credential — normally an organization
API key created in the dashboard under **Settings → API keys**. See
[Authentication](/home/authentication).

```
Authorization: Bearer <credential>
```

## Endpoints

| Group | Endpoints |
| --- | --- |
| Consent | `POST /v1/consent/consumer_identity`, `GET /v1/consent/consumer_identity/{consent_id}`, `PUT /v1/consent/consumer_identity/{consent_id}`, `POST /v1/consent/business_identity` |
| Entities | `GET /v1/entities/consumer_identity/search`, `GET /v1/entities/business_identity/search` |
| KYC certificate | `POST /v1/products/kyc_certificate_snapshot/query`, `POST /v1/products/kyc_certificate_snapshot/query/soft`, `POST /v1/products/kyc_certificate_snapshot/furnish` |
| KYB certificate | `POST /v1/products/kyb_certificate_snapshot/query`, `POST /v1/products/kyb_certificate_snapshot/query/soft`, `POST /v1/products/kyb_certificate_snapshot/furnish` |
| Screening lists | `POST /v1/products/bank_specific_bad_actor_list/query`, `POST /v1/products/cross_bank_financial_crimes_watch_list/query` |
| Coverage check | `POST /v1/products/check` |
| Querying policies | `POST /v1/networks/policies/querying`, `PUT /v1/networks/policies/querying/{policy_id}/configuration` |
| Furnishing policies | `GET /v1/networks/policies/furnishing`, `GET /v1/networks/policies/furnishing/{policy_id}` |
| Graph | `GET /v1/graph/models`, `GET /v1/graph/{resource}`, `GET /v1/graph/{resource}/{object_id}` |
| Mapping dry-run | `/v1/furnishing/mapping/{verify,trace,suggest,propose}` (all `POST`) |
| Attestations | `POST /v1/institution-attestation-event` |
| Monitoring (no auth) | `GET /health`, `GET /version` |

## Conventions

- **Products** expose `query` (read, billable), `query/soft` (non-billable dry
  run, certificates only), and `furnish` (write) operations, for example
  `POST /v1/products/kyc_certificate_snapshot/query`.
- **Querying** a product takes `network_ids` (one or more networks) and
  either a `consent_id` or the subject's profile ID (`consumer_identity_id` /
  `business_identity_id`) — not both. Certificate queries also accept an
  optional `policy_id`. See
  [Querying](/api-overview/querying/overview).
- **Furnishing** a product takes a `network_id` and a list of `records`. See [Furnishing](/api-overview/furnishing/overview).
  Furnishing policies are created and configured in the dashboard; there is no
  REST upload endpoint — bulk files go through the dashboard or
  [SFTP](/api-overview/sftp/overview).
- **Lists** such as entity search take a `limit` of 1–100. Entity search has no
  offset; the graph and furnishing-policy lists also take an `offset`.
- **Errors** follow a consistent JSON shape and include a request ID to quote
  to SOLO — see [Errors](/home/errors).
- **Writes are not idempotent.** There are no idempotency keys; see
  [Retries and idempotency](/home/errors#retries-and-idempotency).
