The **KYB Certificate Snapshot** is a reusable Know Your Business certificate
that packages business-identity, ownership & control (including beneficial
owners), and risk/compliance evidence into a single certificate. A query
assembles the verification work that network participants have already
furnished for a business into one network-issued result.

The certificate supports, and does not replace, your institution's own business
due-diligence program. Whether and how far to rely on a certificate remains
your institution's decision.

| | |
|---|---|
| **Category** | Identity Verification |
| **Use case** | Customer Onboarding |
| **Subject** | Business |
| **Operations** | `POST /v1/products/kyb_certificate_snapshot/query`, `POST /v1/products/kyb_certificate_snapshot/query/soft`, `POST /v1/products/kyb_certificate_snapshot/furnish` |

## What's in the certificate

A KYB certificate consists of three **sub-products**, each a block in the query
response with its own `assertions` (what was attested, and when) and `data`
(the supporting attributes). A certificate is issued only when all three
resolve.

| Sub-product | Response key | What it carries |
|---|---|---|
| Business identity verification | `business_identity_verification` | Registration status, entity type, jurisdiction of formation, tax ID validation result, operational existence, address verification result. |
| Ownership & control verification | `business_ownership_control_verification` | How beneficial owners, control persons, and authorized representatives were determined, how many were identified, and the evidence reviewed. |
| Risk & compliance assessment | `business_risk_compliance_assessment` | Sanctions screening, adverse media, restricted-activity, and activity-risk results, with the screening scope applied. |

Each sub-product is resolved independently and carries the
`furnishing_entity_id` and `attestation_event_id` of the furnished record that
backed it. Shared business descriptors (DBA name, website, jurisdiction of
formation, registration identifier) are repeated in each sub-product's `data`
block so each block stands alone.

## Querying

```bash
curl -X POST https://api.sandbox.solo.one/v1/products/kyb_certificate_snapshot/query \
  -H "Authorization: Bearer $SOLO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "consent_id": "a3f0b9c7-…",
    "policy_id": "5e7d2a14-…",
    "network_ids": ["9f1c0c2e-…"]
  }'
```

The request follows the standard [query anatomy](/api-overview/querying/overview#anatomy-of-a-query):
identify the subject with `consent_id` *or* `business_identity_id` (not both),
and scope the read with `network_ids` plus an optional `policy_id` and
`furnishing_entity_ids`. If you omit `policy_id`, the policy assigned to the
first network in `network_ids` is applied.

- `certificate_id`: the issued certificate, recording its issue date,
  attestation timestamp, and the networks and policy it was resolved under.
- `provenance_event_id`: the billable query event id, also returned in the
  `X-Ref-Id` response header.
- `result`: the consolidated certificate. On a `200`, all three sub-products
  are present.
- `result.meta`: the anchor `network_id` and the `policy_id` that was applied
  (`null` when catalog defaults applied).

`business_registered_address` and `business_operating_address` are currently
always `null`: structured business addresses are not part of the furnished KYB
data yet.

## How the certificate resolves across networks

The query gathers furnished business records across every network in
`network_ids`, applies one querying policy to all of them (the `policy_id` you
pass, or the policy assigned to the first network), and selects the
**oldest matching record** from any listed network for each sub-product. The
result's `meta.network_id` is anchored to the **first** network in your request.
List your primary network first.

## When you get a 204

The endpoint returns `204 No Content` when *no certificate could be created
because the available data did not satisfy the policy*. You'll receive a `204`
when:

- any of the three sub-products (identity, ownership & control, or
  risk/compliance) has no furnished record in the queried networks that passes
  the policy's filters, for example because it was never furnished or is older
  than the policy's freshness window, or
- you passed an explicit `policy_id` that selects specific data fields, and the
  resolved certificate leaves one of those fields empty.

The body is empty; the `X-Ref-Id` header is still present and the query is
still a recorded, billable event.

## Soft check before you query

`POST /v1/products/kyb_certificate_snapshot/query/soft` takes the same request
body as the query and returns `issuable`, `missing_data_paths`, and
`matched_models` without issuing a certificate, recording a query event, or
returning subject data. It works exactly like the
[KYC soft check](/api-overview/querying/kyc-certificate-snapshot#soft-check-before-you-query);
`matched_models` uses the KYB model names (`BusinessIdentityVerificationEvent`,
`BusinessOwnershipControlVerificationEvent`, `BusinessRiskComplianceEvent`).

```bash
curl -X POST https://api.sandbox.solo.one/v1/products/kyb_certificate_snapshot/query/soft \
  -H "Authorization: Bearer $SOLO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "business_identity_id": "b9e1f7c3-…",
    "network_ids": ["9f1c0c2e-…"]
  }'
```

## Furnishing

Participants contribute KYB data with
`POST /v1/products/kyb_certificate_snapshot/furnish`. You must be a furnisher or
governor of `network_id`. Each record needs `federal_ein` and
`business_jurisdiction_of_formation`, which together identify the business, and
can nest verification events (`business_identity_verification_events`,
`business_ownership_control_verification_events`,
`business_risk_compliance_events`):

```json
{
  "network_id": "9f1c0c2e-…",
  "records": [
    {
      "federal_ein": "12-3456789",
      "business_jurisdiction_of_formation": "DE",
      "business_legal_name": "Acme Coffee LLC",
      "business_identity_verification_events": [
        {
          "is_identity_verified": true,
          "identity_verification_timestamp": "2026-05-02",
          "registration_status": "active"
        }
      ]
    }
  ]
}
```

The response lists the profile each record was matched to (or created as), in
request order, and the number of rows persisted per event type:

```json
{
  "success": true,
  "profile_ids": ["b9e1f7c3-…"],
  "counts": { "business_identity_verification_events": 1 }
}
```

Bulk contribution is also available via
[file upload](/api-overview/furnishing/file-upload) and
[SFTP](/api-overview/sftp/overview); see [Furnishing](/api-overview/furnishing/overview)
for the full model.

### KYBCertificateSnapshot (policy configuration only)

These certificate-level fields appear when configuring a
[querying policy](/concepts/governance/querying-policies). They are not
projected into the query response, and they are not applied when a query
resolves: each successful query issues a new certificate dated the day it is
issued.

| Field | API name | Type |
|---|---|---|
| Certificate As Of Date | `certificate_as_of_date` | Date |
| Certificate Attestation Timestamp | `certificate_attestation_timestamp` | Datetime |
| Days Since Certificate As Of Date | `days_since_certificate_as_of_date` | Integer |
| Is Business Identity Verification Performed | `is_business_identity_verification_performed` | Boolean |
| Is Business Ownership Control Performed | `is_business_ownership_control_performed` | Boolean |
| Is Business Risk Compliance Assessed | `is_business_risk_compliance_assessed` | Boolean |
