This guide walks you through your first SFTP upload end-to-end — from registering an SSH key to confirming that the network ingested your data.

## What you'll need

<Steps>
  <Step title="A SOLO dashboard account">
    You register SSH keys in the SOLO dashboard. Start in sandbox: sign in at [app.sandbox.solo.one](https://app.sandbox.solo.one) (see [Getting access](/home/quickstart#getting-access)).
  </Step>
  <Step title="An SSH key pair">
    SFTP sign-in uses an SSH key, not a password. Use an `ssh-ed25519` key, or `ssh-rsa` of at least 2048 bits. Create one for the system that will upload:

    ```bash
    ssh-keygen -t ed25519 -f ~/.ssh/solo_sftp -C "nightly-export"
    ```

    This writes the private key to `~/.ssh/solo_sftp` and the public key to `~/.ssh/solo_sftp.pub`. Only the public key is shared with SOLO.

    <Warning>
      Treat the private key like any other credential. Store it in a secrets manager and never commit it to source control. Anyone holding a registered private key can upload as your organization.
    </Warning>
  </Step>
  <Step title="The network id">
    The network you're furnishing into. Each SFTP feed's detail page in the dashboard shows it. Your organization must be a furnisher or governor of that network.
  </Step>
  <Step title="An SFTP client">
    Anything that speaks SFTP with SSH key authentication works — the `sftp` command from OpenSSH, [FileZilla](https://filezilla-project.org/), [Cyberduck](https://cyberduck.io/), or a library such as Python's [Paramiko](https://www.paramiko.org/).
  </Step>
</Steps>

## Step 1 — Pick an environment

We recommend doing your first upload against **sandbox**. Sandbox is a separate environment from production: nothing you upload there reaches production data, so it's the right place to learn the format and verify your pipeline.

Each environment has its own SFTP server and its own dashboard, where you register that environment's keys:

| Environment | SFTP host                   | Dashboard                                             |
|-------------|-----------------------------|-------------------------------------------------------|
| Sandbox     | `sftp.api.sandbox.solo.one` | [app.sandbox.solo.one](https://app.sandbox.solo.one) |
| Production  | `sftp.api.solo.one`         | [app.solo.one](https://app.solo.one)                 |

Both servers listen on port 22.

## Step 2 — Register your SSH key

<Steps>
  <Step title="Open the SFTP keys page">
    In the dashboard, open **Settings → SFTP keys**.
  </Step>
  <Step title="Add the public key">
    Enter a label that names the system using the key, paste the contents of `~/.ssh/solo_sftp.pub` — the whole line, starting `ssh-ed25519` — and select **Add key**.
  </Step>
  <Step title="Wait for it to sync">
    The key is listed as **Pending** until the server accepts it, usually within a minute, and then as **Synced**. The page updates on its own while a key is pending.
  </Step>
  <Step title="Note your username">
    Once your first key syncs, the **Connection** section of the page shows your SFTP username. Every key your organization registers signs in with this same username.
  </Step>
</Steps>

## Step 3 — Connect

Connect with the username from Step 2 and the private key that matches the registered public key:

<CodeGroup>

```bash sftp (CLI)
sftp -i ~/.ssh/solo_sftp <username>@sftp.api.sandbox.solo.one
```

```python Python (paramiko)
import paramiko

client = paramiko.SSHClient()
client.load_system_host_keys()  # the server's host key must already be in known_hosts
client.connect(
    "sftp.api.sandbox.solo.one",
    port=22,
    username="<username from Settings → SFTP keys>",
    key_filename="/path/to/solo_sftp",
)
sftp = client.open_sftp()
# ... upload here ...
sftp.close()
client.close()
```

```text ~/.ssh/config
Host solo-sftp-sandbox
    HostName sftp.api.sandbox.solo.one
    User <username from Settings → SFTP keys>
    Port 22
    IdentityFile ~/.ssh/solo_sftp
```

</CodeGroup>

The first time you connect from a machine, your SSH client asks you to confirm the server's host key. Accept it to add the server to `known_hosts`; libraries such as Paramiko expect it to be there already.

On a successful connection you'll land at the root of your organization's upload area.

<Tip>
  If the server rejects you with `Permission denied (publickey)`, the most common causes are (1) the key is still **Pending**, (2) the key was registered in the other environment's dashboard, (3) the username doesn't exactly match the one on the **SFTP keys** page, or (4) your client is offering a different key — pass the private key explicitly with `-i`. Reach out to your account manager if it persists.
</Tip>

## Step 4 — Write a JSONL file

Every upload is a [JSONL file](/api-overview/furnishing/file-upload): UTF-8 text with one JSON object per line. Each record carries a `_type` naming the kind of record it is — that's how the network decides which mappings receive it.

Find the record type in the dashboard: open **Feeds**, pick the feed you're delivering, and read its sample record. The sample's `_type` is the value to use, and its other fields are the ones the feed's mapping reads.

For this walkthrough, write one consumer record for a feed whose record type is `consumers`:

```text first_upload.jsonl
{"_type":"consumers","ssn":"123456789","dob":"1990-01-15","first_name":"Jane","last_name":"Doe"}
```

A few things to know about the format ([full reference](/api-overview/furnishing/file-upload#file-format)):

- **One compact object per line** — not a JSON array, and not pretty-printed across lines.
- **Blank lines are skipped.** Every other line is processed independently, so a single bad line won't fail the rest of the file.
- **Identifiers are strings.** Write SSNs and tax identifiers as `"012345678"`, never as numbers — a number drops the leading zero.
- **Filenames** — use a new filename for every upload (a date or batch number works well).

## Step 5 — Upload

Put the file in `network_{network_id}/jsonl_furnish_data/`, where `{network_id}` is the network the records go to. Create the folders the first time you upload to a network:

<CodeGroup>

```bash sftp (CLI)
sftp> mkdir network_9f1c0c2e-7a44-4f1e-9d2a-08b6f3a1c5d7
sftp> cd network_9f1c0c2e-7a44-4f1e-9d2a-08b6f3a1c5d7
sftp> mkdir jsonl_furnish_data
sftp> cd jsonl_furnish_data
sftp> put first_upload.jsonl
sftp> bye
```

```python Python (paramiko)
network_dir = "network_9f1c0c2e-7a44-4f1e-9d2a-08b6f3a1c5d7"
for directory in (network_dir, f"{network_dir}/jsonl_furnish_data"):
    try:
        sftp.mkdir(directory)
    except OSError:
        pass  # already exists
sftp.put("first_upload.jsonl", f"/{network_dir}/jsonl_furnish_data/first_upload.jsonl")
```

</CodeGroup>

<Tip>
  Uploading under a name that already exists replaces that file, and the new copy is ingested again. Use a new filename for every drop.
</Tip>

## Step 6 — Verify ingestion

Ingestion starts automatically once the upload completes and runs in the background. Each file has 30 minutes to finish; split very large exports into several files.

Check the result in the [SOLO dashboard](https://app.sandbox.solo.one) (or [production](https://app.solo.one)): the **Uploads** page lists every file your organization has sent, with the records read and the succeeded, filtered, failed, and unmatched counts. The feed's detail page shows its recent deliveries and names any record types no mapping claimed.

<Note>
  Re-sending is safe for identities: records resolve to the existing consumer or business on their natural keys (SSN and date of birth for consumers; federal EIN and jurisdiction of formation for businesses), so a re-upload attaches to the same profiles instead of creating duplicates. Verification events in a re-sent record are added again, so re-send only the records that didn't ingest.
</Note>

## Common first-upload issues

<AccordionGroup>
  <Accordion title="The dashboard won't accept the key">
    Paste the public key (the `.pub` file), not the private key, as a single line starting with `ssh-ed25519` or `ssh-rsa`. RSA keys must be at least 2048 bits. A key that's already registered is refused, and an organization can register at most 10 keys — remove one you no longer use first.
  </Accordion>
  <Accordion title="No username on the SFTP keys page">
    The username appears once your first key syncs. While a key is **Pending** the page keeps checking; wait a minute and look again.
  </Accordion>
  <Accordion title="Permission denied (publickey)">
    Confirm the key shows **Synced** in this environment's dashboard, the username matches the **SFTP keys** page exactly, and your client is using the matching private key (`sftp -i ~/.ssh/solo_sftp …`). Keys registered in sandbox don't work against production, and the reverse.
  </Accordion>
  <Accordion title='"Host key verification failed"'>
    Your SSH client doesn't know the server's host key yet. Connect once with the `sftp` command and accept the fingerprint at the prompt, or add it to `known_hosts` before connecting:
    ```bash
    ssh-keyscan sftp.api.sandbox.solo.one >> ~/.ssh/known_hosts
    ```
  </Accordion>
  <Accordion title="File uploaded but no upload appears in the dashboard">
    The file landed outside a `jsonl_furnish_data/` folder, so it was never ingested. Re-upload it into `network_{network_id}/jsonl_furnish_data/`.
  </Accordion>
  <Accordion title="Records are counted as unmatched">
    No active mapping in the target network claims their `_type`. Compare the value with the feed's sample record, confirm the feed's mapping is active rather than a draft, and confirm the folder names the network you expected.
  </Accordion>
  <Accordion title="The upload fails with an access error">
    Your organization doesn't hold the furnisher or governor role in the network named by the folder. Check the network id in the path, or ask the network's governor to add your organization as a furnisher.
  </Accordion>
  <Accordion title="Only part of a large file was ingested">
    The file ran out of its 30-minute processing budget or stopped partway. Records processed before that point stay ingested. Check the upload's results, then upload the remaining records as a new file.
  </Accordion>
</AccordionGroup>
