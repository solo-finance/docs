**Entitlement** is what decides *which data* you may read about an entity. It is
the most granular layer of SOLO's access model:

| Layer | Grants | Question it answers |
|---|---|---|
| [Network membership](/concepts/governance/network-roles) | **Capability** | *May I call this kind of operation on this network at all?* |
| [Consent](/concepts/identity/consent) | **Permission** | *May I query this particular subject?* |
| **Entitlement** | **Visibility** | *Of the data that exists, which records and fields may* ***I*** *see?* |

Membership lets you ask; consent makes the question lawful; entitlement decides
what the answer contains. Holding a role on a network — even the governor role —
never makes another participant's data visible on its own.

## What you can read

Every read SOLO serves on your behalf — a product query or an entity search —
applies the same rules, in this order:

<Steps>
  <Step title="Network scope">
    Only data furnished into the networks named in your request is
    considered, and your organization must hold a membership on each of them.
  </Step>
  <Step title="Records you furnished">
    Records your organization furnished are always readable by you, in full.
  </Step>
  <Step title="Records another participant furnished">
    A record another organization furnished is readable only when an active
    grant on one of your consents names that organization as its
    `furnishing_entity_id`. Sharing a network with the furnisher is not enough.
  </Step>
  <Step title="Model-level consent">
    On a record another organization furnished, the data fields of each model
    are returned only when an active grant on one of your consents lists that
    model. Without one, those fields come back empty. Identifiers, links, and
    timestamps are never withheld this way.
  </Step>
</Steps>

## Consent grants

A **model access grant** is attached to a [consent](/concepts/identity/consent)
record and returned when you create or read the consent:

```json
{
  "consent_id": "a3f0b9c7-2d14-4e8a-9b6f-1c0e7d5a3f92",
  "model_access_grants": [
    {
      "furnishing_entity_id": null,
      "models": ["fraud_verification_event"],
      "effective_from": "2026-06-09",
      "effective_to": null
    }
  ]
}
```

| Grant field | Meaning |
|---|---|
| `furnishing_entity_id` | The organization whose furnished records the grant opens to you. `null` means the grant isn't tied to a furnisher and opens no one's records. |
| `models` | The data models whose fields the grant covers, e.g. `fraud_verification_event`. Grants are model-level: a grant covers every data field of each model it lists. |
| `effective_from` / `effective_to` | The dates between which the grant applies. `effective_to` of `null` means open-ended. |

A grant only applies while its consent is valid: once the consent's
`expires_at` has passed, its grants stop applying.

Every consumer consent created through the API carries one grant — the
**default grant** shown above. It covers `fraud_verification_event`, isn't tied
to a furnisher, and runs from the day the consent was created with no end date.
Business consents carry no grant.

## Entitlement records

Alongside these rules, SOLO keeps a per-participant record of the subjects each
participant has engaged with:

- **Furnishing.** Each furnish records which records it created for the
  subject, attributed to your organization.
- **Querying.** When a query issues a certificate, SOLO records which records
  the certificate was built from, attributed to your organization.

These entitlement records make the subject's profile visible to you — for
example in [entity search](/concepts/identity/entities#searching-for-entities)
— and form the audit trail of what you contributed and read. They do not, on
their own, make another participant's records readable; that takes a grant
naming the furnisher, as described above.

Three properties follow:

- **Per subject.** Furnishing one consumer earns you nothing about a different
  consumer, even one furnished by the same institution into the same network.
- **Per participant.** Entitlement attaches to *your* organization. It isn't
  shared across a network or transferred when roles change.
- **Persistent.** Entitlement records don't expire. Consent, by contrast, can
  expire — and you always need a valid consent (or a direct identity lookup)
  to query in the first place.

## Putting it together

A query result is shaped by three things:

<Steps>
  <Step title="Consent">
    You identify the subject with a valid [consent](/concepts/identity/consent)
    record created in one of the networks you query.
  </Step>
  <Step title="Querying policy">
    The network's [querying policy](/concepts/governance/querying-policies)
    decides which furnished verifications qualify to build the result.
  </Step>
  <Step title="Entitlement">
    Of the qualifying records, you receive only those you're allowed to read
    under the rules above.
  </Step>
</Steps>

<Note>
  This is why two participants can run the *same* query on the *same* subject
  and get *different* results: the policy is shared, but what each participant
  may read is decided per participant.
</Note>

## Worked examples

### Example A: a furnisher reads back its own data

Coastal Bank furnishes a KYC record for Jane Doe into its network, including a
document capture event:

```bash
curl -X POST https://api.sandbox.solo.one/v1/products/kyc_certificate_snapshot/furnish \
  -H "Authorization: Bearer $SOLO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "network_id": "9f1c0c2e-7a44-4f1e-9d2a-08b6f3a1c5d7",
    "records": [
      {
        "first_name": "Jane",
        "last_name": "Doe",
        "date_of_birth": "1990-01-15",
        "social_security_number": "123-45-6789",
        "document_capture_events": [
          { "is_document_captured": true, "document_type": "drivers_license" }
        ]
      }
    ]
  }'
```

When Coastal later queries Jane, the records it furnished are readable to it,
so they can back the certificate. (A certificate issues only once the furnished
events cover what the product requires.) A response, trimmed to one
sub-product:

```json
{
  "certificate_id": "0d3c5a7e-6f21-4b9a-8c47-3e2f1a0b9d64",
  "consumer_identity_id": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "result": {
    "meta": { "network_id": "9f1c0c2e-7a44-4f1e-9d2a-08b6f3a1c5d7", "policy_id": null },
    "document_capture": {
      "furnishing_entity_id": "7c2d91e4-5a6b-4c8d-9e0f-1a2b3c4d5e6f",
      "assertions": { "document_capture_assertion": true },
      "data": { "document_type": "drivers_license" }
    }
  }
}
```

### Example B: another member gets nothing

Summit Bank, a member of the same network with a valid consent for Jane, runs
the *identical* query. Summit has furnished nothing about Jane, and none of its
consents carries a grant naming Coastal, so none of Coastal's records are
readable to it. With nothing to build a certificate from, the query returns
**`204 No Content`**.

The query was authorized (membership plus consent), so this is not an error: an
entitlement gap looks like *missing data*, not like a `403`. Run the same
request against the product's `/query/soft` endpoint to see which data is
missing without being billed.

## What entitlement is not

- **Not a role.** Being a
  [governor](/concepts/governance/networks#permissions--roles) of a network
  does not entitle you to members' data.
- **Not network containment.** Sharing a network with another participant does
  not let you read what they furnished.
- **Not retroactive by configuration.** Changing roles or network settings
  does not grant access to data you couldn't already read.

## Troubleshooting: "why is this data missing?"

Work down this checklist when a query returns `204` or a field you expected is
empty:

1. **Was the data furnished at all, into a network you queried?** Data is
   network-bounded, and entitlement filters existing data — it can't surface
   something nobody contributed. A
   [coverage check](/api-overview/querying/coverage-check) tells you whether
   data exists before you spend a query.
2. **Who furnished it?** Your own furnished records are always readable to you.
   Another participant's records need an active grant naming that participant.
3. **Is the model covered?** For records you didn't furnish, check the
   consent's `model_access_grants`: is the model listed in `models`, is today
   inside `effective_from`/`effective_to`, and has the consent expired?
4. **Does the record qualify under the querying policy?** The policy decides
   which furnished verifications can back a result — see
   [Querying Policies](/concepts/governance/querying-policies).

If all four check out and the data is still missing, contact your SOLO account
manager with the `X-Ref-Id` header from the response.
