A **product** is a standardized, named data set that you can **query** (read) and
**furnish** (write) through the network. Products give every participant a common
schema for a given verification domain, so data furnished by one participant can
be queried by another without bespoke integration.

## The query / furnish pattern

Every product supports the same two operations:

<CardGroup cols={2}>
  <Card title="Query" icon="magnifying-glass">
    **Read** consolidated data for an entity, drawn from what authorized
    participants have furnished. Requires a [consent](/concepts/consent) ID.
  </Card>
  <Card title="Furnish" icon="arrow-up-from-bracket">
    **Contribute** verified data for an entity into a network, making it available
    for future queries by entitled participants.
  </Card>
</CardGroup>

```
POST /products/{product}/query
POST /products/{product}/furnish
```

Some products also accept bulk furnishing via spreadsheet upload
(`/products/{product}/furnish_via_upload`) or [SFTP](/sftp/overview).

## Catalog

Products fall into a few families. The exact set available to you depends on the
networks you belong to.

### Certificates

Consolidated, multi-attribute verification results for an entity.

| Product | Subject | Description |
|---|---|---|
| KYC Certificate | Consumer | Consolidated Know Your Customer result — identity, document, biometric, address, and liveness signals. |
| KYB Certificate | Business | Consolidated Know Your Business result — legal entity, ownership, and risk signals. |

Certificates can be furnished as structured JSON or via Excel upload, and queried
as a single consolidated record.

### Screening lists

Read-only lists you query against an entity.

| Product | Subject | Description |
|---|---|---|
| Bank-Specific Bad Actor List | Consumer / Business | Entities flagged by a specific institution. |
| Cross-Bank Financial Crimes Watch List | Consumer / Business | Entities flagged across participating institutions. |

## Querying a product

A product query reads consolidated data for one entity. It needs:

- a **consent ID** identifying the subject and your permission to query it, and
- a **network + policy** scope telling the network where to read from and which
  reading rules apply.

```json
{
  "consent_id": "a3f0b9c7-…",
  "network_policy": [{ "network_id": "9f1c0c2e-…", "policy_id": "5e7d2a14-…" }]
}
```

What comes back is limited to the fields you are [entitled](/concepts/entitlement)
to read and what the network's querying [policy](/concepts/policies) permits. See
[Querying](/concepts/querying) for the full resolution flow.

## Furnishing a product

Furnishing contributes one or more records for an entity into a network.

```json
{
  "network_id": "9f1c0c2e-…",
  "program_name": "default",
  "application_date": "2026-05-28",
  "records": [
    {
      "first_name": "Jane",
      "last_name": "Doe",
      "date_of_birth": "1990-01-15",
      "social_security_number": "123-45-6789"
    }
  ]
}
```

The network matches each record to an entity and stores the furnished data under
your organization. See [Furnishing](/concepts/furnishing).

## Products and policies

A product defines *what* data exists. A [policy](/concepts/policies) defines, per
network, *which parts* of that product a participant may read or write. The same
product can behave differently in two networks because each network attaches its
own policies.
