An **entity** is the subject of a verification: the person or organization you
are furnishing data about or querying data for. Every furnish and every query in
the SOLO Network is about a specific consumer or business — you never operate
on data in the abstract.

<CardGroup cols={2}>
  <Card title="Consumers" icon="user">
    Individual people, identified by name, date of birth, email, and SSN.
  </Card>
  <Card title="Businesses" icon="building">
    Legal entities, identified by legal name, jurisdiction of formation, registration number, and federal EIN.
  </Card>
</CardGroup>

Each subject is held as a **profile**. When you furnish, the network matches
the identity you supply to an existing profile on its natural key, so
contributions from different participants accumulate on one subject rather
than fragmenting into duplicates.

## How entities come into existence

You never call a "create entity" endpoint. Profiles materialize as a side effect
of normal participation:

<Steps>
  <Step title="Furnishing data">
    When you [furnish](/api-overview/furnishing/overview) — for example with
    `POST /v1/products/kyc_certificate_snapshot/furnish` — each record is
    matched to an existing profile on its natural key (SSN **and** date of
    birth for consumers; federal EIN **and** jurisdiction of formation for
    businesses). If none matches, a new profile is created.
  </Step>
  <Step title="Creating consent">
    When you create a [consent](/concepts/identity/consent) record without
    pointing at an existing profile, a new profile is created from the
    consent's identity details.
  </Step>
  <Step title="Linking an existing profile">
    Consent creation accepts an optional `consumer_identity_id` (or
    `business_identity_id`). If you've already found the subject via search,
    pass its `id` and the consent links to that profile instead of creating a
    new one.
  </Step>
</Steps>

## Consumers

A consumer profile holds:

| Field | Notes |
|---|---|
| `first_name`, `last_name` | Legal name |
| `date_of_birth` | ISO `YYYY-MM-DD`. Part of the match key. |
| `personal_email` | |
| `social_security_number` | Part of the match key. |

Phone numbers, addresses, identity documents, and verification events are
separate records attached to the profile — see the
[consumer graph](/concepts/trust/consumer-graph).

<Tip>
  Furnishing matches a consumer on SSN and date of birth **together**. A record
  with the right SSN but a different date of birth creates a different
  profile.
</Tip>

## Businesses

A business profile holds:

| Field | Notes |
|---|---|
| `business_legal_name` | Registered legal name |
| `business_dba_name` | Optional "doing business as" name |
| `business_jurisdiction_of_formation` | e.g. a US state. Part of the match key. |
| `business_registration_identifier_from_jurisdiction_of_formation` | Registration number issued at formation |
| `federal_ein` | Federal EIN, as a string. Part of the match key. |
| `business_entity_type`, `business_date_of_incorporation` | |
| `business_email`, `business_phone`, `business_website_url` | |
| `employee_count` | |

## Searching for entities

Before furnishing or querying, look up subjects that already exist with the
search endpoints:

- `GET /v1/entities/consumer_identity/search`
- `GET /v1/entities/business_identity/search`

Both endpoints share the same mechanics:

- **`network_id` is required.** Search is scoped to a single
  [network](/concepts/governance/networks), and returns only subjects visible
  to you in that network. Your organization must be a member.
- **All identity parameters are optional** and combine with AND — every
  criterion you supply must match.
- **`limit`** caps results between 1 and 100, defaulting to 20. There is no
  offset parameter; narrow your criteria rather than paging.

### Match semantics

Each search parameter has a fixed matching rule:

| Kind | Parameter | Match |
|---|---|---|
| Consumer | `first_name` | Case-insensitive partial |
| Consumer | `last_name` | Case-insensitive partial |
| Consumer | `personal_email` | Case-insensitive partial |
| Consumer | `social_security_number` | Exact |
| Consumer | `date_of_birth` | Exact (`YYYY-MM-DD`) |
| Business | `business_legal_name` | Case-insensitive partial |
| Business | `business_dba_name` | Case-insensitive partial |
| Business | `business_email` | Case-insensitive partial |
| Business | `federal_ein` | Exact (string) |

Partial matching means `first_name=jan` matches both "Jan" and "Janet";
exact-match fields like SSN and EIN must be supplied in full.

### Searching consumers

```bash
curl -G https://api.sandbox.solo.one/v1/entities/consumer_identity/search \
  -H "Authorization: Bearer $SOLO_TOKEN" \
  --data-urlencode "network_id=9f1c0c2e-7a44-4f1e-9d2a-08b6f3a1c5d7" \
  --data-urlencode "first_name=Jane" \
  --data-urlencode "last_name=Doe" \
  --data-urlencode "limit=10"
```

A `200 OK` returns an array of matching profiles:

```json
[
  {
    "id": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
    "identifier": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
    "created_at": "2026-05-02T18:21:44.310000+00:00",
    "updated_at": "2026-06-01T09:03:12.778000+00:00",
    "first_name": "Jane",
    "last_name": "Doe",
    "personal_email": "jane@example.com",
    "date_of_birth": "1990-01-15",
    "social_security_number": "123-45-6789"
  }
]
```

| `id` | UUID | The consumer profile's identifier |
| `identifier` | string | Same value as `id` |
| `created_at` | string \| null | When the profile was created |
| `updated_at` | string \| null | When the profile last changed |
| `first_name` | string \| null | |

| `personal_email` | string \| null | |
| `date_of_birth` | string \| null | `YYYY-MM-DD` |
| `social_security_number` | string \| null | |

<Note>
  Search returns **core identity fields only** — enough to confirm you have the
  right subject. It is not a data product: verification data comes back
  through [product queries](/api-overview/querying/overview), gated by consent
  and entitlement. Search applies the same
  [entitlement](/concepts/governance/entitlement) rules as queries, so fields
  of a profile another organization created can come back empty.
</Note>

## From search to consent: find or create

The search endpoints exist primarily to support a **find-or-create** workflow
before consenting and querying a consumer:

<Steps>
  <Step title="Search first">
    Call `GET /v1/entities/consumer_identity/search` with the strongest identifiers you
    hold (SSN and date of birth where possible).
  </Step>
  <Step title="Found a match? Link it">
    Pass the result's `id` as `consumer_identity_id` when calling
    `POST /v1/consent/consumer_identity`. The consent attaches to the existing profile,
    keeping the subject's history consolidated.
  </Step>
  <Step title="No match? Let consent create the profile">
    Omit `consumer_identity_id`. The identity payload on the consent request creates and
    links a fresh consumer profile.
  </Step>
  <Step title="Query with the consent_id">
    Use the returned `consent_id` on [product queries](/api-overview/querying/products) for
    that subject.
  </Step>
</Steps>

See [Consent](/concepts/identity/consent) for the full consent API.

## Provenance: one entity, many furnishers

An entity profile is a **shared subject**, not a record you own. Several
participants can furnish data about the same consumer or business — one
contributes identity verification outcomes, another fraud events, a third
business registration details. All of it attaches to the same profile, and
each record stays attributed to the participant that furnished it.

Two consequences follow:

1. **You don't control the whole profile.** When your furnish matches an
   existing profile, the profile keeps its existing identity fields and your
   verification events are added alongside other participants'. Nothing you
   furnish overwrites another participant's records.
2. **What you can read is governed, not automatic.** Sharing a profile with
   another furnisher does not mean you see their data. Your own furnished
   records are always readable to you; another participant's are readable only
   under the rules in [Entitlement](/concepts/governance/entitlement).

<Note>
  Identifying an entity tells the network *who* you mean. Consent and entitlement
  determine *what* you may read about them. The same search result can yield
  very different query responses for two different participants.
</Note>

For how each furnisher's contribution stays attributed, see
[Provenance](/concepts/trust/provenance).

## Network scoping

Entities are always handled in the context of a network:

- Search requires a `network_id` and only surfaces subjects visible to you in
  that network.
- Consent records are created against a `network_id`, and the same subject
  needs separate consent per network.
- Furnishes target one network, and queries read only the networks they name.

If you participate in multiple networks, treat each as a separate scope — an
entity you can see in one network is not automatically visible in another. See
[Networks](/concepts/governance/networks) for how membership and roles work.

## Common questions

<AccordionGroup>
  <Accordion title="My search returned an empty array — what does that mean?">
    No profile visible to you in that network matched **all** of your criteria.
    Remember that criteria combine with AND: `first_name=Jane` plus
    `last_name=Smith` only matches profiles satisfying both. Try fewer or
    looser criteria, or double-check exact-match fields (`social_security_number`,
    `date_of_birth`, `federal_ein`) for typos — partial input never matches an
    exact-match field.
  </Accordion>
  <Accordion title="What if I get multiple matches?">
    Partial matching on names and emails can surface several candidates.
    Disambiguate with the exact-match identifiers — SSN and date of birth for
    consumers, federal EIN for businesses — before linking a profile to a
    consent record.
  </Accordion>
  <Accordion title="Can I list entities without any criteria?">
    Yes. All identity parameters are optional, so a request with only
    `network_id` returns up to `limit` profiles (default 20, max 100). For
    production matching, always pass the strongest identifiers you hold.
  </Accordion>
</AccordionGroup>
